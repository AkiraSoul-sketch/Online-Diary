# Сервис аутентификации/авторизации

## Контекст аутентификации.

---

Описание контекста: Аутентификация проверяет личность субъекта, который пытается получить доступ к функционалу в системе. Она отвечает на вопрос "кто ты?", а именно являешься ли ты пользователем системы или нет.

### Основные сущности:

#### Subject.

Описание: Сущность `subject` - это какой-то актор, действующий субъект, пользователь. Какой конкретно - не важно, может быть и человек, и сервис. В рамках этого сервиса мы будем рассматривать `subject` как пользователя, который может быть аутентифицирован и авторизован для выполнения определенных операций.

#### Subject session

Описание: `subject session` - это _аутентифицированная_ сессия. Она создается при успешной аутентификации субъекта (успешной проверки логина + пароля или email + пароля). Сессия контролирует время жизни аутентификации. То есть, когда есть `subject session` для `subject`, то он считается аутентифицированным. Сессия может быть активной, истекшей или удаленной. В рамках сессии может быть выдан `access token` и `refresh token`, которые используются для авторизации при выполнении операций.

### Модель данных:

_Subject_:

| id   | login  | email  | password_hash | archived | email_confirmed | created_at | updated_at | deleted_at |
| ---- | ------ | ------ | ------------- | -------- | --------------- | ---------- | ---------- | ---------- |
| uuid | string | string | string        | boolean  | boolean         | datetime   | datetime   | datetime   |

_Subject session_:

| id   | subject_id | refresh_token | refresh_token_expires_at |
| ---- | ---------- | ------------- | ------------------------ |
| uuid | uuid       | string        | datetime                 |

### Функционал (API) в рамках контекста аутентификации:

1. `register_subject()` - регистрация субъекта. Когда создается пользователь, то создается субъект. Этот функционал может вызываться путем обработки сообщения из брокера сообщений. Либо, для начала, можно напрямую, при регистрации пользователя создавать субъект, то есть, создание субъекта = создание пользователя.

2. `authenticate_subject()` - аутентификация субъекта. В этом месте проверяется пароль + логин, или пароль + email. При успешной аутентификации создается `subject session` и выдается `access token` и `refresh token`.

3. `refresh()` - обновление `access token` для `subject_session` через `refresh token`. Если `refresh token` валиден, то создается новый `access token` и обновляется `refresh token`, иначе - требуется повторная аутентификация (удаление `subject session`).

4. `logout()` - выход из системы. Удаление конкретной `subject session` и связанных с ним токенов.

5. `logout_all()` - выход из системы на всех устройствах. Удаление всех `subject session` для конкретного `subject`.

6. `update_subject()` - обновление данных субъекта. Например, изменение пароля, email, логина. При этом, если изменяется пароль, то все `subject session` для этого субъекта удаляются, тем самым требуя повторную аутентификацию.

7. `verify_email()` - подтверждение email. При регистрации субъекта, его email может быть не подтвержден. Для подтверждения email может быть отправлено письмо с ссылкой для подтверждения. При переходе по этой ссылке вызывается этот функционал, который устанавливает флаг `email_confirmed` в `true`.

8. `archive_subject()` - архивирование субъекта. Этот функционал может использоваться для деактивации субъекта. Пример: пользователь удаляет свой аккаунт, и вместо удаления записи в таблице, истории и связей, мы просто устанавливаем флаг `archived` в `true`, тем самым делая его неактивным. По истечении определенного времени, можно удалить такие записи из базы данных.

### Правила:

1. Для `subject` должен быть уникальный `login` и `email`.
2. Для `subject` у которого `archived` = `true`, не должна быть возможности аутентифицироваться, даже если пароль верный.
3. `Subject` у которого `email_confirmed` = `false`, не должна быть возможность аутентифицироваться, даже если пароль верный.

## Контекст сервисов, операций, прав, отношений и объектов.

Микросервисы регистрируют свои операции. Для того чтобы сделать микросервис авторизации/аутентификации более универсальным и независимым от конкретных решений, он может предоставлять возможность другим микросервисам объяснить, какие у них есть операции, и какие права нужны для этих операций, чтобы контролировать доступ к своему функционалу. Помимо этого, могут быть критичные объекты, доступ к которым мы тоже хотим предоставлять только при определенных условиях. Например при наличии связи edit с subject.

### Основные сущности:

#### Namespace.

Описание: `namespace` - это логическая область (микросервис, маленький контекст бизнес-операций). Он нужен для того, чтобы разграничивать операции и права между разными микросервисами. Например, у нас может быть `users-service`, `gradebook-service` и т.д. Каждому микросервису соответствует свой `namespace`, чтобы разделять, с чем имеется дело.

#### Operation.

Описание: `operation` - это конкретная бизнес-операция (функционал, команда), которая выполняется в этом `namespace`, то есть в этом микросервисе. Например, операции: "поставить оценку", "изменить оценку" - будут принадлежать `gradebook-service`, а операции "создать пользователя", "удалить пользователя" - будут принадлежать `users-service`.

#### Permission.

Описание: `permission` - это право. Это может быть право на чтение, редактирование, удаление, создание и т.д. Например, для операции "поставить оценку" может быть право "gradebook.grade.create". Для операции "изменить оценку" может быть право "gradebook.grade.edit". Для операции "создать пользователя" может быть право "users.create". Permission формируется как `namespace` + `operation`, соединяются два эти названия через символ ".".

#### Operation required permission.

Описание: `operation required permission` - это привязка права к операции. Она нужна чтобы выразить, что для выполнения конкретной операции, нужно иметь конкретное право. Например, для операции "поставить оценку" нужно иметь право "gradebook.grade.create". Для операции "изменить оценку" нужно иметь право "gradebook.grade.edit". Для операции "создать пользователя" нужно иметь право "users.create".

#### Object.

Описание: `object` - это критичный объект, доступ к которому нужно контролировать.

#### Relation.

Описание: `relation` - это связь между субъектом и объектом. Она нужна для того, чтобы выразить, что конкретный субъект имеет определенное отношение к конкретному объекту.

#### Subject object realtion

Описание: `subject object relation` - это связь между субъектом и объектом, которая выражает, что конкретный субъект имеет определенное отношение к конкретному объекту. Например, если у нас есть операция "изменить оценку", то объектом может быть конкретный журнал и конкретный преподаватель и связь между ними - "edit". И тогда, для того, чтобы разрешить пользователю выполнять операцию "изменить оценку", мы должны проверить, что у него есть отношение subject:123 - edit -> journal:456, где subject - какой-то пользователь, journal - конкретный журнал, а edit - связь между ними, которая разрешает выполнять операцию "изменить оценку" в этом журнале.

#### Функционал (API) в рамках контекста сервисов, операций и прав:

1. `register_namespace()` - Микросервис может зарегистрировать свою область, указав её название. Пример: микросервис "gradebook-service" регистрирует свой namespace "gradebook" или "users-service" регистрирует свой namespace "users".

2. `register_operation()` - Микросервис может зарегистрировать свою операцию, указав её название. Пример: микросервис "gradebook-service" регистрирует операцию "grade.create", "grade.edit", а микросервис "users-service" регистрирует операцию "users.create", "users.delete".

3. `register_permission()` - Микросервис может зарегистрировать своё право, указав его название. Пример: микросервис "gradebook-service" регистрирует право "create", "edit", "export" а микросервис "users-service" регистрирует право "create", "delete".

4. `assign_permission_to_operation()` - Микросервис может назначить право на операцию. Таким образом его операция будет защищена и для её выполнения нужно будет иметь определенное право. Пример: микросервис "gradebook-service" назначает право "create" на операцию "grade.create", а микросервис "users-service" назначает право "delete" на операцию "users.delete".

5. `remove_namespace()` - Микросервис может удалить свою область, указав её название. Например, если микросервис "gradebook-service" больше не нужен, то он может удалить свой namespace "gradebook", конкретно - сделать себя archived.

6. `remove_operation()` - Микросервис может удалить свою операцию, указав её название. Например, если микросервис "gradebook-service" больше не нуждается в операции "grade.edit".

7. `remove_permission()` - Микросервис может удалить своё право, указав его название. Например, если микросервис "gradebook-service" больше не нуждается в праве "edit".

8. `update_namespace()` - Микросервис может обновить свою область, указав её название. Например, если микросервис "gradebook-service" хочет переименовать свой namespace "gradebook" в "grades".

9. `update_operation()` - Микросервис может обновить свою операцию, указав её название. Например, если микросервис "gradebook-service" хочет переименовать свою операцию "grade.create" в "grade.add".

10. `update_permission()` - Микросервис может обновить своё право, указав его название. Например, если микросервис "gradebook-service" хочет переименовать своё право "create" в "add".

11. `create_relation()` - Микросервис может создать связь. Например, микросервис "gradebook-service" создает связь "edit".

12. `create_object()` - Микросервис может создать объект. Например, микросервис "gradebook-service" создает объект "journal:456".

13. `remove_object()` - Микросервис может удалить объект. Например, микросервис "gradebook-service" удаляет объект "journal:456".

14. `remove_relation()` - Микросервис может удалить связь. Например, микросервис "gradebook-service" удаляет связь "edit".

### Модель данных:

namespace:

| id   | name   | archived |
| ---- | ------ | -------- |
| uuid | string | boolean  |

operation:

| id   | namespace_id | name   | archived |
| ---- | ------------ | ------ | -------- |
| uuid | uuid         | string | boolean  |

permission:

| id   | namespace_id | name   | archived |
| ---- | ------------ | ------ | -------- |
| uuid | uuid         | string | boolean  |

operation_required_permission:

| operation_id | permission_id |
| ------------ | ------------- |
| uuid         | uuid          |

object:

| id   |
| ---- |
| uuid |

relation:
| id | name |
| ---- | ------ |
| uuid | string |

subject_object_relation:
| subject_id | object_id | relation_id |
| ---------- | --------- | ----------- |
| uuid | uuid | uuid |

### Правила:

1. Для `namespace` должно быть уникальное название. Например, не может быть двух `namespace` с названием "gradebook".
2. Для `operation` должно быть уникальное название в рамках одного `namespace`. Например, не может быть двух `operation` с названием "grade.create" в рамках `namespace` "gradebook".
3. Для `permission` должно быть уникальное название в рамках одного `namespace`. Например, не может быть двух `permission` с названием "create" в рамках `namespace` "gradebook".
4. Для `operation required permission` должно быть уникальное сочетание `operation_id` и `permission_id`. Например, не может быть двух записей с одинаковым `operation_id` и `permission_id` в таблице `operation_required_permission`.
5. Для `relation` должно быть уникальное название. Например, не может быть двух `relation` с названием "edit".

## Контекст ролей.

Описание: Роли - это набор прав. Они нужны для того, чтобы упростить управление правами. Вместо того, чтобы назначать права каждому пользователю на каждую операцию, мы можем создать роли, которые будут содержать определенные права, и назначать эти роли пользователям. Например, роль "admin" может содержать все права, роль "teacher" может содержать права на создание и редактирование оценок, а роль "student" может содержать право на чтение оценок.

### Основные сущности:

#### Role (роль).

Описание: `role` - это набор прав. Роль может быть назначена пользователю, и тогда пользователь будет иметь все права, которые входят в эту роль.

#### Role permission (право роли).

Описание: `role permission` - это связь между ролью и правом. Она нужна для того, чтобы выразить, какие права входят в конкретную роль.

#### Subject role (роль субъекта).

Описание: `subject role` - это связь между субъектом (пользователем) и ролью. Она нужна для того, чтобы выразить, какие роли назначены конкретному пользователю.

### Функционал (API) в рамках контекста ролей:

1. `register_role()` - микросервис создает запись в таблице ролей, которая содержит информацию о роли. Например, микросервис "gradebook-service" регистрирует роль "teacher", "student".

2. `update_role()` - микросервис может обновить роль, указав её название. Например, если микросервис "gradebook-service" хочет переименовать роль "teacher" в "instructor".

3. `remove_role()` - микросервис может удалить запись из таблицы ролей, тем самым удалив роль. Например администратор удаляет роль "teacher", которая больше не нужна.

### Модель данных:

`Role`:

| id   | namespace_id | name   | archived |
| ---- | ------------ | ------ | -------- |
| uuid | uuid         | string | boolean  |

### Ограничения:

1. Для `role` должно быть уникальное название в рамках одного `namespace`. Например, не может быть двух `role` с названием "teacher" в рамках `namespace` "gradebook".

## Общие связи между контекстами:

`Role_permission` - это связь между `role` и `permission`, которая выражает, какие права входят в конкретную роль. Например, роль "teacher" может содержать права "gradebook.grade.create", "gradebook.grade.edit".

`Subject_role` - это связь между субъектом (пользователем) и ролью. Она нужна для того, чтобы выразить, какие роли назначены конкретному пользователю.

### Общая модель данных для `role_permission` и `subject_role`:

role_permission:

| role_id | permission_id |
| ------- | ------------- |
| uuid    | uuid          |

subject_role:
| subject_id | role_id |
| ---------- | ------- |
| uuid | uuid |

### Общий функционал (API):

1. `assign_permission_to_role()` - микросервис создает запись в таблице: role_permission, которая связывает роль, операцию и право. Таким образом, для выполнения операции пользователю нужно будет иметь право и проверить мы можем это запросом к этой таблице. Например, микросервис "gradebook-service" назначает право "create" на операцию "grade.create" для роли "teacher".

2. `assign_subject_to_role()` - микросервис создает запись в таблице: subject_role, которая связывает пользователя и роль. Например, микросервис "gradebook-service" назначает роль "teacher" пользователю с id = 123.

3. `create_subject_object_relation()` - Микросервис может создать связь между субъектом и объектом. Например, микросервис "gradebook-service" создает связь между subject:123 и journal:456 с типом связи "edit".

4. `check_object_relation()` - Микросервис может проверить наличие связи между субъектом и объектом. Например, микросервис "gradebook-service" проверяет наличие связи между subject:123 и journal:456 с типом связи "edit", чтобы разрешить выполнение операции "изменить оценку".

5. `remove_subject_object_relation()` - Микросервис может удалить связь между субъектом и объектом. Например, микросервис "gradebook-service" удаляет связь между subject:123 и journal:456 с типом связи "edit".

6. `check_operation_access()` - Микросервис может проверить, разрешено ли субъекту выполнять операцию. Для этого он должен проверить, что у субъекта есть роль, которая содержит право, которое нужно для выполнения операции.

### Правила:

1. Для `role_permission` должно быть уникальное сочетание `role_id` и `permission_id`. Например, не может быть двух записей с одинаковым `role_id` и `permission_id` в таблице `role_permission`.
2. Для `subject_role` должно быть уникальное сочетание `subject_id` и `role_id`. Например, не может быть двух записей с одинаковым `subject_id` и `role_id` в таблице `subject_role`.
3. Для `subject object relation` должно быть уникальное сочетание `subject_id`, `object_id` и `relation_id`.
